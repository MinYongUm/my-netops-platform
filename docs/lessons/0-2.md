# Lesson 0-2 — install.sh

## 목표

`./install.sh` 한 번으로 Lesson 0-1의 수작업(Zabbix 초기 설정, Grafana 데이터소스 등록)을 재현한다. 두 번 실행해도 결과가 같아야 한다.

## 결과

- `docker compose down -v` + `.env` 삭제 상태에서 `./install.sh` → Grafana Explore 그래프 조회까지 사람 손 없이 약 21초 (ldevu01 기준)
- 재실행 시 변경 없음 (모든 항목 "이미 있음", 토큰 재발급 없음)
- 토큰·비밀번호는 저장소에 없음

## 결정 사항

- Zabbix/Grafana API 호출은 Python 표준 라이브러리만 사용 (`urllib`, `json`). pip 불필요
  - 이유: v0.2 inventory에서 Zabbix API 클라이언트를 재사용. bash로 JSON 조립·파싱하면 이스케이프가 지저분해짐
  - jq는 Ubuntu 기본 패키지가 아님. python3는 기본
- Grafana 데이터소스는 provisioning 파일이 아니라 HTTP API로 등록
  - 이유: provisioning은 토큰을 환경변수(.env 또는 compose)에 넣어야 함. API는 토큰이 Python 메모리에서 Grafana 암호화 저장소로 바로 감
- 토큰 재발급 정책: 데이터소스가 있고 health OK면 아무것도 안 함. 없거나 health 실패면 `token.generate` 후 생성(POST) 또는 갱신(PUT)
- Zabbix Admin 비밀번호는 `.env`의 `ZBX_ADMIN_PASSWORD`. 첫 실행 때 기본값 `zabbix`에서 이 값으로 변경
- 포트 점검은 netops 스택이 이미 떠 있으면 건너뜀 (재실행 시 우리 컨테이너가 포트를 잡고 있으므로)

## 구성

### install.sh

| 순서 | 내용 |
|---|---|
| 1 | docker, docker compose v2, python3, openssl 존재 확인 |
| 2 | `.env` 없으면 `.env.example` 복사 + 비밀번호 3개 `openssl rand -hex 16`, 권한 600. 있으면 건드리지 않음 |
| 3 | `=change_me` 남아 있으면 중단. `.env.example`의 키가 `.env`에 다 있는지 확인 |
| 4 | 포트 점검 (스택 실행 중이면 건너뜀) |
| 5 | `docker compose up -d --wait` |
| 6 | `python3 scripts/bootstrap.py --env-file .env` |

`.env` 생성이 compose 호출보다 앞에 있어야 한다. compose.yaml이 `${VAR:?}` 형식이라 `.env` 없이는 `docker compose ps`도 실패한다.

### scripts/bootstrap.py

| 함수 | 하는 일 |
|---|---|
| `wait_for_zabbix` | `apiinfo.version` 성공할 때까지 3초 간격 재시도 (최대 120초) |
| `login_admin` | `.env` 비밀번호로 로그인. 실패하면 `zabbix`로 로그인 후 변경, 재로그인 |
| `get_id` | `Zabbix servers`(호스트 그룹), `User role`(역할) 이름 → ID |
| `ensure_usergroup` | `grafana` 그룹, `Zabbix servers` 읽기 전용(permission 2) |
| `ensure_user` | `grafana` 사용자, User role. 비밀번호는 난수 생성 후 버림 |
| `ensure_token` | `grafana` 토큰 틀 |
| `wait_for_grafana` | `/api/health`가 `database: ok`일 때까지 재시도 |
| `enable_plugin` | Zabbix 앱 활성화 |
| `ensure_datasource` | 데이터소스 생성/갱신 + health 검증 |

모든 ensure 함수는 `get(filter 이름)` → 있으면 건너뜀 → 없으면 `create`.

## 수작업 기록 — 자동화 전에 손으로 한 API 호출

Zabbix (호출 형식은 전부 동일, `method`와 `params`만 다름):


## Troubleshooting

### .env 없을 때 compose 변수 에러 14줄

- 증상: `.env` 없이 실행하면 `required variable ... is missing a value` 가 대량 출력. exit code는 0
- 원인: 포트 점검의 `docker compose ps -q`가 compose.yaml을 파싱하는데 `${VAR:?}` 변수가 없음. `$(...)` 안이라 실패가 묻힘
- 해결: `.env` 생성을 첫 compose 호출보다 앞으로 옮김

### nano 붙여넣기로 스크립트가 두 번 실행됨

- 증상: 출력에 `[OK] 사전 점검 완료#!/usr/bin/env bash` 가 보이고 모든 단계가 두 번 찍힘
- 원인: 기존 내용을 지우지 않고 새 내용을 붙여넣어 두 스크립트가 한 파일에 이어짐. 이어진 shebang이 줄 맨 앞이 아니라 `grep -c '^#!'`로는 1로 나옴
- 해결: `: > 파일`로 비운 뒤 붙여넣기. 확인은 `grep -c 'usr/bin/env bash'`(앵커 없이)와 `wc -l`

### change_me 검사가 정상 .env를 거부

- 증상: `.env` 자동 생성 직후 `change_me 가 남아 있습니다`로 중단
- 원인: `.env.example` 주석에 `change_me` 단어가 있어 `grep -q change_me`가 주석 줄을 잡음
- 해결: `grep -q '=change_me$'`로 값 위치만 검사

### Healthy인데 API 호출 실패

- 증상 1 (Zabbix): `apiinfo.version: Unable to select configuration.`
- 원인 1: `--wait`는 zabbix-web 컨테이너 healthcheck(웹 서버 응답)까지만 기다림. DB 스키마는 zabbix-server가 만드는 중. `apiinfo.version`도 DB를 읽음
- 증상 2 (Grafana): `ConnectionResetError: [Errno 104] Connection reset by peer`
- 원인 2: 첫 기동 때 기본 플러그인 다운로드 중 HTTP가 끊김
- 해결: bootstrap.py에 `wait_for_zabbix`, `wait_for_grafana` (3초 간격, 최대 120초)

### ConnectionResetError가 traceback으로 출력됨

- 증상: 에러 한 줄 대신 traceback 전체
- 원인: `main()`이 `URLError`, `TimeoutError`만 잡음. `ConnectionResetError`는 둘 다 아님
- 해결: 연결 관련 예외는 전부 `OSError`의 하위 클래스이므로 `except OSError`로 통일

### 확인 출력에 세션 토큰 전체가 노출

- 증상: `user.login` 결과를 `cut -c1-60`으로 잘랐는데 32자 토큰이 다 보임
- 해결: 해당 세션 `user.logout`. 이후 `cut -c1-30` 또는 `${#VAR}`(길이)로만 확인

## What I Learned

- Zabbix API는 실패해도 HTTP 200. `error` 키로만 판단한다. Grafana는 상태 코드(404, 409)로 알려준다. 클라이언트 설계가 달라지는 이유
- Zabbix `create`는 멱등이 아니다. 두 번째 호출은 `already exists` 에러. 그래서 항상 `get` → `create`
- 이름 조회는 `filter`(정확 일치). `search`는 부분 일치라 멱등 체크에 쓰면 안 됨
- Zabbix 토큰 문자열은 `token.generate` 응답에서 한 번만 볼 수 있다. 다시 부르면 이전 것은 무효
- 컨테이너 Healthy는 "서비스 사용 가능"이 아니다. 실제 API로 확인해야 한다
- urllib은 4xx/5xx를 `HTTPError` 예외로 던지고, `HTTPError`는 `URLError`의 하위 클래스. 안 잡으면 404가 연결 실패로 보인다
- 자동화 전에 손으로 해봤기 때문에 대기 문제를 미리 짐작만 하고, 실제 에러 메시지를 본 뒤에 고칠 수 있었다
